# Infinity Clicker — результаты бенчмарков

[English version](../../BENCHMARK.md)

Все цифры получены на этой машине встроенным бенчмарком (`InfinityClicker.exe --bench`) и автотестом
(`InfinityClicker.exe --autotest`). Сырые отчёты, сгенерированные программой без ручных правок, лежат в `benchmarks/`:

| Файл | Что это |
|---|---|
| `benchmarks/results/bench_20260924_235228.md` | **полный прогон** (все 9 разделов, стресс по 60 с), 23:40–23:52 |
| `benchmarks/results/bench_20260925_000016.md` | повтор теста видимости кликов (новая методика) и стресс-теста с новой метрикой «время внутри SendInput», 00:00 |
| `benchmarks/results/bench_20260925_000248_quick.md`, `benchmarks/results/cps_matrix.csv` | быстрый повтор SendInput + матрицы CPS в «медленном» состоянии системы, 00:02 |
| `benchmarks/results/autotest_results.md` | последний прогон автотеста (29/30, см. ниже) |

**Тестовая система:** AMD Ryzen AI 9 HX 370 (12 ядер / 24 потока, Zen 5 + Zen 5c), Windows 11 25H2 build 26200.9550,
питание от сети, QPC 10 МГц, текущее системное разрешение таймера 1.0 мс (кто-то из фоновых программ его поднял;
на наш процесс это не влияет — см. раздел 1). Фоном работали Steam, NVIDIA Overlay, Armoury Crate и др.

> ⚠️ **Главный вывод о честности цифр.** Скорость `SendInput` на одной и той же машине в течение часа менялась
> **в 6 раз** (см. раздел 4): от ~0.16 мс до ~1 мс на вызов «клик». Это внешний фактор — глобальные low-level
> хуки других программ, драйверы, фоновая нагрузка. Поэтому «потолок CPS» — свойство *системы в данный момент*,
> а не константа автокликера. Infinity Clicker измеряет это прямо во время работы (метрика «время внутри SendInput»)
> и честно показывает Target vs Actual.

## 1. Таймеры: насколько точно спит Windows

Ошибка ожидания = факт − запрошено, мкс (по 300 замеров, поток HIGHEST):

| Механизм | 1 мс: mean / p99 | 5 мс: mean / p99 | CPU |
|---|---|---|---|
| `Sleep()` без `timeBeginPeriod` | **+14 498 / +15 106** | +10 542 / +11 051 | 0% |
| `Sleep()` + `timeBeginPeriod(1)` | +989 / +1 516 | +890 / +1 509 | 0% |
| `std::this_thread::sleep_for` | **+14 526 / +15 297** | +10 586 / +11 527 | 0% |
| waitable timer (обычный) | +14 529 / +15 143 | +10 567 / +11 121 | 0% |
| **waitable timer HIGH_RESOLUTION** | **+517 / +617** | +426 / +603 | 0% |
| HIGH_RESOLUTION + `timeBeginPeriod(1)` | +526 / +636 | +432 / +600 | 0% |
| HIGH_RESOLUTION + `NtSetTimerResolution(0.5 мс)` | +503 / +600 | +443 / +588 | 0% |
| **гибрид STANDARD (таймер + спин)** | +6.1 / +101.8 | **+0.6 / +1.5** | 54% / 8% |
| **гибрид ULTRA** | **+1.9 / +0.5** | +0.3 / +0.8 | 87% / 23% |
| чистый спин по QPC | +0.0 / +0.1 | +0.0 / +0.2 | 100% |

Выводы:
- Win11 не даёт процессу повышенного разрешения таймера, пока тот сам его не попросит, даже если система уже
  работает на 1 мс. `Sleep(1)` и `sleep_for` реально спят **~15.6 мс**. Любой кликер на них не может выдать больше ~64 CPS.
- HIGH_RESOLUTION-таймер — лучший «спящий» механизм (~0.5 мс ошибки). `timeBeginPeriod` и недокументированный
  `NtSetTimerResolution` ему почти не помогают, поэтому Infinity Clicker их не использует.
- Микросекундная точность достижима только с QPC-спином в конце ожидания.

\* В этом прогоне Received считался как «получено кликов / длительность прогона», а длительность — это N−1 интервалов,
поэтому на малых частотах он выше ровно на один клик (1.11 при 1 CPS = 10 кликов за 9 с). Сами количества совпадают:
окно получило ровно столько кликов, сколько сгенерировано. В текущей версии обе величины считаются одинаково
(N−1 интервалов между первым и последним событием).

Выводы:
- **1–5000 CPS держатся точно**: ошибка среднего интервала ≤ 0.01%, окно получает ровно столько, сколько сгенерировано.
  Утверждение Blur-AutoClicker «лимит Windows ≈ 500 CPS» не подтверждается.
- Выше ~7000/с проявляется разница между «Windows приняла» и «приложение получило». На 10 000 CPS SendInput принял
  8972/с, окно получило 7276/с, остальное потерялось.
- Батч из 64 кликов в одном вызове — патология (в 50 раз медленнее). Поэтому движок догоняет пакетами не больше 8.
- В режиме УЛЬТРА при 1000 CPS джиттер **4 мкс** ценой одного ядра. В режиме СТАНДАРТ при 100 CPS — 0.13 ядра.

С установленным собственным `WH_MOUSE_LL` (так бывает, когда триггер — кнопка мыши): 1000 CPS → 1000.2 получено;
5000 CPS → 4643; MAX → ~4900. Хук стоит примерно −30% пропускной способности, поэтому ставится только когда нужен.

## 4. Пропускная способность SendInput и её нестабильность

Клики из потока бенчмарка прямо в тест-панель, «быстрое» состояние (23:4x) и через ~20 минут:

| Способ вызова | Время вызова, 23:4x | Время вызова, 00:02 | Доставлено кликов/с, 23:4x | Доставлено, 00:02 |
|---|---|---|---|---|
| `SendInput(1)` ×2 на клик | 101 мкс | 662 мкс | 4930 | 755 |
| `SendInput(2)` на клик | 157 мкс | 967 мкс | 6241 | 1034 |
| пакет 8 кликов | 845 мкс | 3353 мкс | 6941 (**18 587 из 24 000 дошло**) | 2386 |
| пакет 64 клика | 58.9 мс | 101.9 мс | 1080 | 624 |

Дополнительные наблюдения:
- После того как пользователь закрыл Discord (в более ранней сессии замеров), `SendInput(2)` ускорился с 333 до 203 мкс.
  Каждое инжектированное событие синхронно проходит через *все* глобальные LL-хуки в системе.
- Внешний процесс (PowerShell), нулевое движение мыши: p50 254 мкс в «медленном» состоянии.
- Стресс-повтор с метрикой «время внутри SendInput» (раздел 8) показал p50 = 3 мс и максимум 35 мс на вызов:
  движок ~100% времени ждал внутри системного вызова. Сам Infinity Clicker в это время грузил CPU на 0.07–0.15 ядра.
- При пакетной отправке окно-приёмник может потерять часть событий (18 587 из 24 000): очередь ввода потока
  переполняется. Счётчики Input Lab показывают это как разницу между «Принято» и «Получено».

## 6. Удержание DOWN→UP: кто увидит короткий клик

Повтор с исправленной методикой (00:00): 37 кликов/с, 120 кликов в строке, частоты не кратны частотам опроса:

| Удержание | Событийное окно (WM_LBUTTONDOWN) | Опрос состояния 1000 Гц | Опрос 60 Гц («раз в кадр») | Ожидание для идеального опроса 60 Гц |
|---|---|---|---|---|
| 0 мкс | **120/120** | 22% | 2% | 0% |
| 1 мс | **120/120** | 32% | 15% | 6% |
| 5 мс | **120/120** | 92% | 6% | 30% |
| 10 мс | **120/120** | 100% | 32% | 60% |
| 16.7 мс | **120/120** | 100% | 62% | 100% |
| 20 мс | **120/120** | 100% | 62% | 100% |

- Событийные приложения — браузеры, обычные программы, GLFW/LWJGL, то есть **Minecraft Java** — получают
  **каждый** клик даже при удержании 0 мкс.
- Игры, которые опрашивают *состояние* кнопки раз в кадр, пропускают короткие клики. Для них ставьте УДЕРЖАНИЕ ≥
  длительности кадра (10–20 мс). Поэтому в профилях по умолчанию стоит 10–12 мс.
- В «медленном» состоянии системы Windows доставляет DOWN и UP пачками, поэтому опрос видит меньше теоретического
  (у 1000 Гц при 1 мс — 32% вместо 100%). Короткие удержания делают клики чувствительными к нагрузке ОС.

## 9. Функциональные приёмочные тесты (`--autotest`)

Запускается реальное приложение с интерфейсом и изолированной папкой данных; физический ввод симулируется
инжекцией с отдельным тегом. При нормальном состоянии системы — **30 из 30**. Таблица собрана из двух
прогонов подряд: первого (29/30, до исправления Numpad 7) и второго (30/30, после исправлений; строки «CPS за 1 с»,
«Numpad 7» и «MAX» взяты из него).

| Проверка | Результат |
|---|---|
| Hold, триггер F13 удерживается 500 мс при 100 CPS | 51 нажатие / 51 отпускание, остановка через **0.4 мс** |
| Toggle, триггер «кнопка мыши 4» | включился, 61 клик за ~300 мс при 200 CPS, выключился |
| Burst 10 / Fixed Count 25 / Duration 500 мс при 200 CPS | ровно 10 / 25 / 100 |
| 10 / 50 / 1000 CPS в течение 1 с | 10 / 50 / 1000 получено, actual 10.00 / 50.00 / 999.90 |
| Клавиша A ×20 скан-кодом | 20 нажатий с vk=A scan=0x1E, 20 отпусканий |
| Комбинация Ctrl+Shift+K ×5 | 5 нажатий K с зажатыми Ctrl+Shift, модификаторы отпущены |
| Клавиши F5, Space, Up, Numpad 7, «.» | по 3 из 3 |
| Кнопки мыши Right, Middle, 4, 5, колесо вверх/вниз | по 5 из 5 |
| Нет feedback loop: триггер «левая кнопка» + действие «левый клик» | работает, пока кнопка зажата, ровно 1 запуск |
| Аварийная остановка Ctrl+Shift+F12 при зажатой кнопке | остановка за **1.9 мс**, снят с охраны, `VK_LBUTTON` отпущена |
| Нет залипших клавиш: остановка посреди удержания Ctrl+A | Ctrl был зажат, после остановки Ctrl и A отпущены |
| Фильтр активного окна | чужое окно впереди: пауза, 0 кликов; целевое впереди: 40 кликов |
| MAX 3 с: интерфейс не зависает | 5024 CPS, 15 072 из 15 072 получено; отклик UI p99 **0.7 мс**, max 4.2 мс |
| Простой (взведён, окно видно) | **0.0042 ядра** (0.4% одного ядра, 0.018% машины) |
| Профили и настройки сохраняются и загружаются | ок |
| Ресурсы после всех тестов | +2.5 МБ, +13 хэндлов (шрифты, окна), +1 поток (пул Windows) |

Найдено и исправлено по ходу тестов:
- **Numpad 7 превращался в Home**: при выключенном NumLock скан-код 0x47 — это Home. Цифры numpad теперь
  инжектируются по VK, со скан-кодом.
- **Actual CPS коротких прогонов** считался как N / время и давал 11.1 вместо 10. Теперь считается как
  (N−1) интервалов между первым и последним действием.

Последний прогон (00:04, «медленное» состояние системы): 29/30. Не прошёл только «1000 CPS за 1 с» — окно получило
466 кликов, потому что Windows в тот момент блокировала SendInput на ~2 мс на вызов. MAX в том же прогоне дал всего
539 CPS. Тест корректно фиксирует, что цель в таких условиях недостижима.

**Защита от залипания при убийстве процесса** (`InfinityClicker.exe --kill-test`): процесс зажимает Left Shift и завершается
через `TerminateProcess` без какой-либо очистки. Результат: Shift был зажат до убийства, после — **отпущен
процессом-сторожем**.

```bat
InfinityClicker.exe --bench quick      :: быстрый (~3 мин)
InfinityClicker.exe --bench only=timer,margin    :: отдельные разделы
InfinityClicker.exe --autotest         :: приёмочные тесты (~30 с)
```

Во время замеров не трогайте мышь и клавиатуру. Закройте программы с глобальными хуками (Discord, оверлеи),
если нужен максимум пропускной способности.
